## 2. 개요
- 타깃 사용자: 지원 전에 채용 공고를 찾아보는 청년 구직자, 특히 신입 구직자
- 사용자 장면(가설): 신입 구직자가 SV Career 홈에 들어와 "지금 뭐 뽑고 있지?"를 확인하려 하지만, 공고 글까지 가는 길이 멀어서 떠날 수 있다. 이 장면은 인터뷰나 사용자 테스트로 아직 검증하지 않았다.
- 핵심 문제(가설): 홈에서 공고 글까지의 접근 경로가 길어서 공고를 보지 못하고 떠나는 사용자가 있다. GA 기준 방문 44명 중 공고 글을 연 사람은 6명(13.6%)이다. 이 수치만으로 경로 길이가 원인이라고 말할 수 없다.
- 해결 방향: 홈 첫 화면에서 공고를 바로 보고 고를 수 있게 하고, 질문에 답하면서 공고 글로 연결한다.
- 이번 해결 범위: 홈에서 공고 글까지의 접근 경로. 교육 정보와 청년정책은 이번 범위에서 뺀다.

## 3. 문제 정의
### 3.1 현황 근거
- 기간: 2026-10-27 ~ 11-23 (GA4 스냅샷)
- 방문 44명, 공고 글 열람 6명(13.6%), 완독 5명, 지원 클릭 2명(6회)
- 신입 공고 조회 15회(활성 사용자 11명), 경력 공고 조회 12회(활성 사용자 4명). 비교 대상 글은 신입 1건, 경력 1건으로 개수가 같다.
- 주의: 두 글만 비교한 값이라 신입이 더 많이 본다는 결론은 내리지 않는다. 완독률은 유형별로 기록되어 있지 않다.
- 한계: 표본이 작고, 글 열람 이벤트명이 11/18에 바뀌었으며, 관리자 접속이 일부 포함되어 있다. 이 기간의 공고 글은 가상(샘플) 글이었다. 11/24 이후 공고는 고용24 API 데이터로 바뀌므로, 변경 후 지표는 새 기준선으로 본다.

### 3.2 후보 문제 3개
1. 홈에서 공고 글까지의 접근 경로가 길다
2. 공고를 읽고도 지원으로 이어지지 않는다
3. 신입과 경력 구직자의 정보 요구가 달라 보이는데 맞춰 주지 못한다

### 3.3 우선순위 결정
- 선택한 문제: 1번 (홈에서 공고 글까지의 접근 경로)
  - 사용자가 겪을 수 있는 장면이라고 가정하며, 글 열람 비율이라는 기록이 있다. 장면 자체는 아직 검증하지 않았다.
  - 홈 구성을 바꾸면 바로 해결 방안과 연결된다.
- 탈락한 문제와 이유
  - 2번: 지원 완료는 고용24 상세 페이지에서 일어나 우리 사이트에서 보이지 않는다. 다만 외부 지원 페이지로 넘어간 클릭은 측정할 수 있으므로, 이 방식으로 지원 의도를 본다.
  - 3번: 신입 공고와 경력 공고 두 개만 비교한 근거라서, 측정을 보강한 뒤 다음 단계에서 검토한다.

### 3.4 최종 문제 정의 (문제, 타깃, 솔루션 흐름)
- 문제(가설): 신입 구직자는 SV Career 홈에서 공고를 보고 싶지만, 소개와 날씨 영역을 지나야 공고 글에 닿는다. 이 경로 때문에 원하는 공고를 찾지 못하고 떠날 수 있다.
- 타깃: 지원 전에 공고를 찾아보는 신입 구직자. 공고 조건을 빨리 확인하고 싶어 하며, 설명을 꼼꼼히 읽기보다 바로 보고 싶어 한다.
- 솔루션 연결: 홈 첫 화면에 질문 도우미와 공고 목록을 두고, 질문 답변에서 공고 글로 바로 넘어가게 한다. 이 두 가지가 문제 하나(접근 경로)를 직접 줄이는 기능이다.
- 선택 이유: 세 후보 중 이 문제만 사용자 행동 데이터(글 열람 비율)와 화면 구조가 함께 근거가 된다. 나머지 두 문제는 검증할 근거가 부족하다. 다만 이 근거는 샘플 기간의 가상 글 데이터이므로 강하지 않다.

## 4. 해결 방안
- 홈 상단 소개 블록 제거 (11/24 반영)
- 홈에서 질문과 공고가 바로 보이도록 배치 (시안 A 채택, 일부 로컬 구현)
- 기대 효과: 홈 방문 대비 공고 글 열람 비율 증가

### 4-0. 구현 상태 (11/24 14:00 기준, 로컬 구현 후 배포 전)
- 배포됨(main 푸시 완료): 사이트명 SV Career 변경, 공채 속보 이벤트(job_list_view, job_item_click), 질문 챗봇(규칙 기반), 챗봇 캐릭터 선택, 챗봇 배치(오른쪽 중간, 모바일은 하단 시트)
- 로컬 구현 완료(아직 배포 안 함): 홈 배너 제거와 제목 한 줄, 채용 드롭다운 필터(제목 대괄호 태그), 교육 과정 API(310L01) 패널을 채용 패널 옆 두 칸으로 배치, 이벤트 job_filter_change와 edu_list_view, edu_item_click 추가
- 계획 (아직 미구현): 공고 자동 슬라이드(4초), 챗봇을 홈 상단 카드로 옮기기(현재는 오른쪽 중간 버튼), API 실패 시 안내 문구
- 아직 확인되지 않은 것: 교육 정보 API 활용신청 승인 여부, 훈련기관명 항목

### 4-1. AI 기능: 신입 구직자용 질문 챗봇 (선택)
- 목적: 신입 구직자가 공고와 교육 내용을 질문하면 답을 주고, 답과 함께 관련 공고나 글로 바로 연결한다. (흐름: 질문 → 답 → 관련 글 연결)
- 문제와의 연결: 질문에 답하는 데서 끝나지 않고, 답과 함께 **관련 공고나 글로 가는 링크**를 보여 줘서 공고 글까지 가는 경로를 줄인다.
- 데이터 범위: 고용24 공채속보 API의 목록 정보만 사용한다. 교육 과정 API는 승인 후 추가한다. 샘플 글은 모두 삭제해 답변 데이터에 포함되지 않는다. 공고 본문은 아직 가져오지 않는다.
- 제외 범위: 대출, 국가 지원사업, 청년정책 정보는 다음 단계로 미룬다.
- AI를 쓰지 않은 이유: (1) 공고와 글이 샘플 수준이라 생성형 답변이 근거 없는 내용을 만들 위험이 크다. (2) AI 키를 브라우저에 두면 누구나 볼 수 있어 보안 문제가 생긴다. (3) 키 없이 GitHub Pages에서 바로 동작해야 한다. 따라서 답은 블로그 글에서만 찾는다. 다음 단계에서 글이 충분히 쌓이면 요약 기능을 검토한다.
- 구현 방식: 외부 AI 키를 쓰지 않는 규칙 기반 검색으로 구현했다. 현재 검색 대상은 블로그 글이며, 공고 데이터 검색은 다음 단계다. 키가 없어 브라우저에 민감한 값이 없고, GitHub Pages와 Vercel 두 주소에서 모두 동작한다. 처음 검토한 서버 함수 방식은 키 관리와 설정 부담이 커서 제외했다.
- 캐릭터: 직접 만든 남성, 여성 캐릭터 두 명 중 선택한다. 기본값은 남성이고, 선택은 브라우저에만 저장한다. 외부에서 가져온 이미지는 출처와 권리가 불분명해 쓰지 않았다.
- 한계: 목록 API에는 자격 조건이 없어서, 자격에 대한 질문은 "상세 공고에서 확인하세요"라고 안내한다.
- 데이터 한계: 공고 목록 정보만으로 답할 수 있는 질문이 제한된다. 답을 찾지 못하면 "찾을 수 없습니다"와 공고 목록 링크를 보여 준다. 챗봇이 블로그 글을 검색하는 구조는 샘플 글 삭제 후 공고 데이터 검색으로 바꾸는 것이 다음 작업이다.
- 검증 방법: 챗봇 답에서 연결된 글을 연 비율과, 공고 글 열람 비율(현재 13.6%)을 비교한다.
- 측정 이벤트(구현 완료, 11/24): `chatbot_open`(챗봇 열기), `chatbot_question`(질문 전송, 찾은 글 수와 캐릭터만 전송), `chatbot_link_click`(답에서 글 링크 클릭), `chatbot_character_change`(캐릭터 변경). 질문 원문은 개인정보 보호를 위해 보내지 않는다.

### 4-2. 디자인 시안과 채택 이유 (11/24)
- **홈 상단 (시안 A 채택)**: 배너를 없애고 "채용과 교육 소식" 제목 한 줄만 남긴다. 그 아래에 챗봇 카드를 둔다.
  - 채택 이유: 첫 화면에 질문과 공고가 함께 보여서 공고까지 가는 경로를 줄인다.
  - 버린 안: 시안 B는 배너 높이가 그대로라 공고가 아래로 밀린다. 시안 C는 캐릭터 두 명을 함께 보여 주기 어렵다.
- **홈 배치 순서 (수정)**: 챗봇 → 채용 공고 목록과 교육 패널을 좌우로 나눈 영역. 자동 슬라이드는 공고 노출만 늘리고 경로를 줄이지 않아 6장에서 보류로 바꿨다.
  - 채택 이유: 클릭하지 않아도 공고가 계속 보이고, 채용과 교육을 한 화면에서 나눠 볼 수 있다.
- **채용 필터 (드롭다운 채택)**: 제목의 대괄호 단어(신입, 경력, 체험형 인턴, 계약직 등)로 목록을 거른다.
  - 채택 이유: 칩은 항목이 많아지면 칸을 많이 차지하지만, 드롭다운은 칸 오른쪽 위에서 공간을 적게 쓴다.
  - 주의: 칩 시안에서는 대괄호를 잘못 읽어 모든 공고가 "기타"로 묶였다. 구현할 때 태그 추출을 테스트로 확인한다.
- **챗봇 위치**: 시안 A처럼 홈 상단에 두는 것을 목표로 한다. 현재 실사이트는 오른쪽 중간 버튼이며, 구현 때 바꾼다.

## 5. 지표
- 핵심 지표: 홈 방문 대비 공고 글 열람 비율
- AI 지표: 챗봇 질문 수 대비 연결 글 클릭 비율 (측정 이벤트 구현 후 확인)
- 보조 지표: 공채 속보 목록 조회 수(job_list_view), 외부 지원 페이지 이동 수(job_item_click, 공고 상세 링크 클릭), 드롭다운 필터 사용 수(job_filter_change)
- 지원 지표 정의: 우리 사이트에서 지원을 접수하지 않는다. 지원 의도는 외부 지원 페이지로 이동한 클릭으로 측정한다. 실제 지원 완료 여부는 알 수 없다.
- 목표: 공고 열람 비율을 기존 기준선 13.6%에서 25% 이상으로 올린다(새 기준선 기준으로 재확인). 25%는 근거가 있는 수치가 아니라 임의로 정한 방향성 목표다. 목표는 표본(44명) 기준의 방향성 목표이며, 근거는 목록 이후 열람이 두 배 가까이 늘면 경로 개선이 의미 있다고 보는 것이다. 통계적 유의성은 주장하지 않는다.
- 측정 방법: GA4 이벤트. 변경 전(10/27~11/23)은 참고용, 변경 후는 새 기준선으로 본다. 두 기간은 같은 기준으로 직접 비교하지 않는다.
- 한계: 표본이 작고, 이벤트 이름 변경 이력이 있어 같은 기준으로 비교하기 어렵다.

## 6. 기능 요구사항 (문제와의 연결 기준)
기능은 많을수록 좋은 것이 아니라, 선택한 문제 하나를 얼마나 직접 줄이는지로 판단한다.

| 기능 | 문제와의 연결 | 상태 |
|---|---|---|
| 질문 도우미 (챗봇) | 직접: 답변에서 공고 글로 바로 연결 | 배포 완료 |
| 채용 드롭다운 필터 | 직접: 원하는 공고 유형을 빨리 찾게 함 | 로컬 구현 완료 |
| 공고 목록 홈 배치 (시안 A 구조) | 직접: 첫 화면에서 공고가 보임 | 로컬 구현 완료, 배치 조정 필요 |
| 교육 과정 API 패널 | 간접: 공고 문제와 직접 관계가 약함 | 보조 기능, 승인 전에는 숨김 |
| 공고 자동 슬라이드 (4초) | 간접: 노출은 늘지만 클릭 경로는 줄이지 않음 | 보류 (구현하지 않음) |

- 공고 링크 클릭을 기록한다. 공고 제목은 보내지 않고 순번만 보낸다.
- 지원 방식: 공고는 고용24 API에서 가져오므로 사이트 안에 지원 폼을 두지 않는다. 각 공고의 상세 링크를 새 탭으로 열어 외부에서 지원하게 한다.
- 성공 기준: 홈에서 공고 글 열람까지 필요한 클릭이 줄었는지, 위 지표가 목표에 가까워졌는지로 판단한다.
- 하지 않은 것: 청년정책 API, 대출 정보, 사이트 안 지원 접수 (공고 주체가 우리가 아니므로 범위 밖)

## 7. 비기능 요구사항
- 공고 API 호출이 실패하면 목록 영역이 사라진다. 개선 필요: 안내 문구 표시
- 고용24 인증키는 Firestore `settings/jobs`에 저장되고, 보안 규칙상 누구나 읽을 수 있다. 호출 주소에도 키가 보인다. 개선 필요: 서버 함수 전환 여부 결정 (Vercel에서만 동작하는 한계가 있음)
- 샘플 채용 글에 있던 지원 폼은 이름과 이메일을 저장하는 구조였다. 공고가 외부 API 기반이라 목적이 맞지 않으므로, 샘플 글 삭제와 함께 제거를 검토한다.

## 10. Q&A
- Q. 왜 지원 전환을 문제로 삼지 않았나요? A. 지원 완료가 외부 사이트에서 일어나 우리가 볼 수 없기 때문입니다. 대신 외부 지원 페이지로 이동한 클릭을 측정합니다.
- Q. 사이트 안에서 지원을 받지 않는 이유는 무엇인가요? A. 공고는 고용24 API에서 가져오고 우리 자체 채용이 없기 때문입니다. 지원 접수는 공고를 낸 곳의 절차를 따릅니다.
- Q. 신입 조회가 많은데 왜 신입 기능을 먼저 만들지 않았나요? A. 공고 2개 비교라서 근거가 약하고, 측정을 먼저 보강하기로 했습니다.
- Q. 왜 배너를 뺐나요? A. 배너가 높아서 공고가 첫 화면 아래로 밀리기 때문입니다. 시안 세 가지를 비교한 뒤 제목 한 줄과 질문 카드를 택했습니다.
- Q. 왜 칩이 아니라 드롭다운인가요? A. 항목이 늘어날 때 칸을 적게 차지하기 때문입니다.
- Q. 디자인은 누가 만들었나요? A. 캐릭터와 화면 구성은 작성자가 직접 시안을 만들었습니다. 캐릭터 이미지 출처는 작성자 본인이며, 외부 이미지는 쓰지 않았습니다.
