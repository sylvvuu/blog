## 2. 개요
신입 구직자는 SV Career 홈에서 채용 공고를 먼저 보고 싶어 한다. 그러나 현재 홈은 소개 영역과 날씨 영역을 지나야 공고 글에 닿는다. GA 기준 방문 44명 중 공고 글을 연 사람은 6명(13.6%)으로, 경로가 길어 떠나는 사용자가 있을 것이라고 본다. 이 경로 가설을 해결하기 위해 홈 첫 화면에 고용24 공고 목록을 바로 보여 주고, Claude API 기반 상담으로 공고 탐색을 돕는다. 채용 공고와 교육 과정은 직접 쓰지 않고 고용24 오픈 API에서 가져온다. 이번 해결 범위는 홈에서 공고까지의 접근 경로이며, 청년정책, 기업 재무 정보, 갭이어 안내, 사이트 안 지원 접수는 범위 밖이다.

## 3. 문제

### 3.1 데스크리서치
- 데이터 현황 (GA4, 10/27~11/23, 샘플 기간)
  - 방문 44명, 공고 글 열람 6명(13.6%), 완독 5명, 지원 클릭(외부 이동) 2명 6회
  - 신입 공고 조회 15회 (활성 사용자 11명), 경력 공고 조회 12회 (활성 사용자 4명)
  - 비교 대상 글은 신입 1건, 경력 1건으로 개수가 같다. 두 글의 차이로 신입 우위를 결론짓지 않는다.
- 한계: 표본이 작고, 글 열람 이벤트명이 11/18에 바뀌었다. 관리자 접속이 일부 섞여 있다. 이 기간의 공고 글은 가상 샘플이었다.

#### 3.1.0 기존 데이터 해석 (GA4 10/27~11/23, 11/24 정리)
| 항목 | 값 | 계산 | 해석 |
|---|---|---|---|
| 공고 글 열람률 | 6 / 44 | 13.6% | 방문자 대부분이 공고 글에 닿지 않음 (H1 근거) |
| 열람자 중 완독 | 5 / 6 | 83% | 공고 글을 연 사람은 대부분 끝까지 읽음 |
| 열람자 중 외부 지원 클릭 | 2 / 6 | 33% | 공고를 연 사람의 3분의 1이 외부 지원 페이지로 이동 (H2 근거) |
| 신입 공고 1인당 조회 | 15 / 11 | 1.4회 | 여러 사람이 한두 번씩 봄 |
| 경력 공고 1인당 조회 | 12 / 4 | 3.0회 | 소수가 여러 번 봄 (관심 집중 가능성, 원인 미확인) |

- 근거로 쓸 수 있는 것: 방문 대비 열람률이 낮다는 점(H1), 열람 후 외부 이동이 일어난다는 점(H2).
- 근거로 쓰지 않는 것: 신입과 경력의 우위 비교 (글 1건씩, 활성 사용자 수가 다름), 이 기간 공고 글이 가상 샘플이었다는 점을 반영하면 열람률의 절대값.
- 다음 확인: 개선 후 같은 표를 같은 방식으로 채운다 (TEST_REPORT 4-2).

#### 3.1.1 4C 분석
- 고객 (Customer): 지원 전 공고를 찾는 신입 구직자 (가설). 공고를 빨리 훑고 싶어 한다.
- 경쟁사 (Competitor): 고용24, 잡코리아, 사람인 등 공고 플랫폼. 우리는 공고를 대신 쌓는 곳이 아니라, 홈에서 공고를 빨리 보여 주는 안내 페이지를 목표로 한다.
- 자사 (Company): 1인 운영. GitHub Pages, Vercel, Firebase를 사용하며 운영 비용이 거의 없다.
- 협력사 (Collaborator): 고용24 오픈 API. 공고와 교육 과정 데이터의 출처이며, 서비스마다 활용신청과 키가 따로 필요하다.

#### 3.1.2 SWOT 분석 (현재 블로그 기준, 추정 포함)
| 구분 | 내용 |
|---|---|
| 강점 | 고용24 공공 API로 실제 공고를 가져올 수 있다. 우리 자체 채용 운영 부담이 없다. |
| 약점 | 방문자와 데이터가 적다. 샘플 기간의 지표만 있다. 챗봇은 블로그 글만 검색해 답할 내용이 거의 없었다. |
| 기회 | 졸업 유예와 취업 준비 청년이 늘고 있다는 관찰이 있다. 공공 데이터로 신뢰도 있는 정보를 줄 수 있다. |
| 위협 | 외부 API 승인과 키 관리에 의존한다. 외부 지원 사이트로 이동하면 전환을 볼 수 없다. |

#### 3.1.3 TOWS 전략
- SO (강점 + 기회): 공공 API 공고 목록을 홈 첫 화면에 배치해 신뢰도 있는 정보를 빠르게 준다.
- WO (약점 + 기회): 적은 데이터는 새 기준선 측정으로 보완하고, 목표 수치는 나중에 정한다.
- ST (강점 + 위협): 공고 조회 키와 AI 키는 서버 환경 변수나 서버 함수에서만 쓰도록 설계한다.
- WT (약점 + 위협): 외부 이동 클릭을 측정해 전환 공백을 줄이고, 채용 키 노출은 서버 함수로 옮기는 것을 다음 단계로 둔다.

### 3.2 문제 발굴
| 번호 | 문제 | 타깃 | 솔루션 방향 |
|---|---|---|---|
| 1 | 홈에서 공고 글까지의 접근 경로가 길다 | 공고를 찾는 신입 구직자 | 홈 첫 화면에 공고 목록과 드롭다운 배치 |
| 2 | 공고를 읽고도 지원으로 이어지지 않는다 | 공고를 읽은 구직자 | 외부 지원 페이지 이동을 측정 (지원 완료는 외부에서 발생) |
| 3 | 신입과 경력의 정보 요구가 다른데 맞춰 주지 못한다 | 신입, 경력 구직자 | 기업 구분 드롭다운으로 나누기 (근거 약함) |

- 위 3개 외에 나온 후보: 졸업 유예 대학생의 진로 선택지(교육, 해외 경험, 국비 과정) 비교 문제. 현재 근거가 없어 가설로만 남긴다.

### 3.3 문제 검증

#### 3.3.1 검증 계획
- 행동 데이터: Microsoft Clarity로 홈의 스크롤과 클릭 위치를 확인한다 (설치 완료, 공개 페이지만).
- 사용자 인터뷰: 신입 구직자 3명에게 홈에서 공고를 찾아보게 하고, 막히는 지점을 기록한다.
- AI 상담 평가: 질문 10개로 답의 정확성과 근거 표시를 확인한다.

#### 3.3.2 검증 결과 및 인사이트
- 행동 데이터: 아직 충분히 쌓이지 않았다. 설치 후 확인 전이다.
- 사용자 인터뷰: 미실시.
- AI 상담 평가: 미실시. Claude API 키 연결 전이다.
- 결론: 문제 1은 가설로 남아 있고, 검증 결과 없이 "해결됨"이라고 쓰지 않는다.

### 3.4 문제 최종 정의

#### 3.4.1 우선순위 결정
- 평가 방식: 2x2 정성 매트릭스. 가로축은 문제 근거가 있는가, 세로축은 이번 범위에서 해결할 수 있는가. 숫자 점수는 쓰지 않는다.
- RICE를 쓰지 않은 이유: 샘플이 적고 도달 수와 신뢰도를 측정하지 못해 점수의 근거가 없다.

| 문제 | 문제 근거 | 해결 가능성 | 위치 | 판단 |
|---|---|---|---|---|
| 1. 접근 경로 | 있음 (GA 6/44, 방향성만) | 높음 (홈 배치) | 근거 있음 · 해결 가능 | 선택 |
| 2. 지원 전환 | 없음 (지원 완료 측정 불가) | 중간 | 근거 없음 · 해결 가능 | 보류 |
| 3. 신입과 경력 | 없음 (비교 글 2건) | 높음 | 근거 없음 · 해결 가능 | 보류 |

- 아이젠하워 매트릭스: 문제 1은 긴급하지는 않지만 중요하다. 제출 일정 안에서 해결 가능한 범위다.
- MoSCoW: 문제 1은 Must, 문제 2의 외부 이동 측정은 Should, 문제 3은 Won't (이번 제출).

#### 3.4.2 문제 최종 정의
- 문제 (가설): 신입 구직자는 SV Career 홈에서 공고를 보고 싶지만, 소개와 날씨 영역을 지나야 공고 글에 닿는다. 이 경로 때문에 원하는 공고를 찾지 못하고 떠날 수 있다.
- 타깃: 지원 전에 공고를 찾아보는 신입 구직자. 공고 조건을 빨리 확인하고 싶어 한다.
- 먼저 고른 문제: 세 문제 중 문제 1(접근 경로)을 먼저 해결하기로 했다.
- 선택 이유
  - 블로그의 약점은 "공고가 있어도 홈에서 바로 보이지 않는다"는 점이다. 이 약점은 사용자가 공고까지 가는 경로에서 직접 생긴다.
  - 문제 1은 화면 배치만 바꾸면 해결할 수 있어서, 제출 기한 안에 검증 가능한 결과를 낼 수 있다.
  - 문제 2(지원 전환)는 지원 완료가 외부에서 일어나 측정할 수 없다. 문제 3(신입과 경력 구분)은 비교할 글이 각 1건뿐이라 근거가 없다.
- 흐름: 문제 1(경로가 길다) → 타깃(공고를 빨리 찾는 신입 구직자) → 솔루션(홈 첫 화면에 공고와 질문 도우미 배치). 3.3의 인터뷰와 AI 평가로 검증한다.
- 근거의 한계: 샘플 기간 데이터라 근거는 약하다. 그래서 새 기준선을 측정한 뒤 목표를 정하고, 이 결정을 다시 검토할 항목으로 남긴다.

## 4. 해결 방안

### 4.1 솔루션 정의
신입 구직자가 SV Career 홈에 들어오면 첫 화면에서 고용24 공고를 바로 보고 고를 수 있게 한다. 공고에 대한 질문은 근거 공고 번호가 붙은 답과 원문 링크로 해결하도록 돕는다.

### 4.2 ASIS / TOBE

| 항목 | ASIS (기존) | TOBE (목표) |
|---|---|---|
| 컨셉 | 소개 배너와 날씨를 지나 글 목록으로 가는 블로그 | 홈에서 공고를 바로 보고 질문하는 채용·교육 안내 |
| 타깃 | 블로그 방문자 전체 (가설) | 지원 전 공고를 찾는 신입 구직자 |
| 비즈니스 모델 | 없음 (개인 포트폴리오) | 없음. 공공 데이터 기반의 무료 안내 |
| 기능 | 샘플 채용·교육 글, 규칙 기반 챗봇 | 채용 목록과 드롭다운, 교육 패널, Claude API 상담 (서버 함수) |
| 디자인 | 배너 중심 | 제목 한 줄, 질문 카드, 두 칸 배치 (시안 A) |

#### 4.2.1 기능 구현 상태
| 기능 | 상태 |
|---|---|
| 채용 목록 (고용24 공채속보 210L21) | 배포 완료 |
| 드롭다운 필터 (API 기업 구분 값) | 배포 완료 |
| 교육 패널 (고용24 310L01) | 로컬 구현, 활용신청 승인 후 표시 |
| 규칙 기반 질문 도우미 (블로그 글 검색) | 배포 완료, 데이터 부족 |
| Claude API 상담 서버 함수 (`api/chat.js`) | 로컬 작성, 키 연결 후 테스트 |
| 외부 지원 페이지 이동 측정 | 배포 완료 (`job_item_click`) |
| 자동 슬라이드, 챗봇 홈 상단 이동 | 보류 |

### 4.3 예상 성과
- 이 솔루션으로 홈에서 공고 목록까지 가는 클릭 수가 줄어든다 (정성 기대).
- 공고 상세 링크 클릭 수가 늘어난다 (`job_item_click`).
- 주의: 목표 수치는 새 기준선을 측정한 뒤 정한다. 13.6%는 샘플 기간 값이라 목표 근거로 쓰지 않는다.

#### OKR
- O: 홈 방문자가 공고를 쉽게 찾게 한다
  - KR1: 새 기준선 측정 후 공고 열람 비율 목표 설정 (측정 기간 2주)
  - KR2: 공고 상세 링크 클릭 수 측정 (기준선 대비 증가 여부 확인)
  - KR3: 상담 평가 질문 10개 중 근거 있는 답 비율 확인 (목표는 결과 확인 후 설정)

## 5. 가설 및 지표

### 5.1 핵심 지표 (Key Metrics)
| 가설 | 지표 | 측정 방법 |
|---|---|---|
| H1. 홈 경로가 길어 공고를 못 본다 | 홈 방문 대비 공고 열람 비율 | GA4, 새 기준선 |
| H2. 공고 목록을 바로 보면 상세 이동이 늘어난다 | 공고 상세 링크 클릭 수 (`job_item_click`) | GA4 |
| H3. 상담 답이 근거 있으면 사용자가 공고를 연다 | 상담 답의 근거 공고 클릭 비율 | GA4 (상담 이벤트는 구현 필요) |

- 보조 지표: 드롭다운 사용 수 (`job_filter_change`), 교육 목록 조회 수 (`edu_list_view`)
- 측정 한계: 표본이 작고, 외부에서 지원이 끝나 실제 지원 완료는 측정하지 못한다.

### 5.2 고객 정의 (Persona)
- 유형 1: 신입 구직자 (1순위): 졸업 예정이거나 졸업 유예 중인 청년. 공고를 빨리 훑고 조건을 확인하고 싶다.
- 유형 2: 경력 구직자 (범위 밖): 이번 제출에서는 다루지 않는다.
- 유형 3: 진로를 고민하는 대학생 (범위 밖): 교육과 해외 경험 정보를 찾는다. 다음 단계에서 검토한다.

### 5.3 마케팅 메시지
- 핵심 카피 (가설): "지금 뽑는 공고, 홈에서 바로 확인하세요."
- 사용 용어: "공채속보", "교육 과정", "외부 지원 페이지". 우리가 공고를 올린 것처럼 쓰지 않는다.
- 메시지 원칙: 공고의 주체는 고용24와 해당 기업이다. 자격과 연봉은 원문에서 확인하라고 안내한다.

## 6. 기능적 요구사항 (Functional Requirements)

### 6.1 주요 기능 리스트
| ID | 기능 | 설명 | 우선순위 |
|---|---|---|---|
| F1 | 채용 목록 | 고용24 공채속보 최신 20건 중 5건 표시 | Must |
| F2 | 드롭다운 필터 | 기업 구분 값(coClcdNm)으로 목록 필터, 기본값 전체보기 | Must |
| F3 | 외부 지원 이동 | 공고 상세 링크를 새 탭으로 열고 클릭 기록 | Must |
| F4 | 교육 패널 | 310L01로 석 달 안에 시작하는 과정 5건 표시, 키 없으면 숨김 | Should |
| F5 | 규칙 기반 질문 도우미 | 블로그 글 검색 (현재 데이터 부족) | Could |
| F6 | Claude API 상담 | 공고 목록을 근거로 질문에 답하고 근거 공고 번호 표시 | Must (이번 제출 핵심) |
| F7 | 관리자 키 설정 | 날씨, 채용, 교육 키를 각각 저장 | Must |
| F8 | 관리자 글 작성 | 일반 글만 작성 (교육과 채용 분류 없음) | Should |

### 6.2 유즈케이스 시나리오
- UC1 (공고 탐색): 신입 구직자가 홈에 들어와 채용 목록을 본다. 드롭다운에서 기업 구분을 고른다. 공고 제목을 누르면 고용24 상세 페이지가 새 탭으로 열린다.
- UC2 (상담): 구직자가 "마감이 가장 가까운 공고는?"이라고 묻는다. 서버가 공고 목록을 가져와 Claude에게 전달한다. 답변에는 근거 공고 번호가 표시되고, 목록에 없으면 "목록에서 찾을 수 없습니다"라고 답한다.
- UC3 (키 설정): 관리자가 관리자 화면에서 채용 키와 교육 키를 각각 저장한다. 키가 없으면 해당 패널이 숨는다.

### 6.3 기능 정의 (상세)
- F6 Claude API 상담
  - 입력: `{ question }`, 1~200자
  - 처리: 질문에서 지역·고용형태 조건을 찾는다. 조건이 있으면 채용 목록 20건에서 명시된 조건을 모두 만족하는 공고만 남긴다 (값이 없는 공고는 제외). 조건이 없으면 기존 근거 목록을 쓴다. 남은 공고를 번호로 붙여 Claude API를 호출하고(모델 `claude-haiku-5-5`), 답의 `[번호]` 중 범위 안의 번호만 근거로 쓴다.
  - 조건에 맞는 공고가 없으면 Claude를 부르지 않고 "현재 조회한 공고에서는 조건에 맞는 결과를 찾지 못했어요" 안내와 조정할 조건 하나를 돌려준다 (`noMatch: true`).
  - 출력: `{ answer, sources: [{ title, source, company, region, employType, endDate, url }] }`
  - 오류: 400 형식 오류, 405 방식 오류, 422 근거 없음, 502 공고 조회 실패, 503 꺼짐 또는 키 없음, 500 기타. 422·502·503·500은 화면이 기존 글 검색으로 돌아간다.
  - 규칙: 공고 목록 안에서만 답한다. 자격, 연봉, 재무는 판단하지 않는다. 질문 원문은 저장하지 않는다.
  - 미확인: 지역(`workRegion`)과 고용형태(`empTpNm`) 필드명은 210L21 실제 응답으로 확인하기 전까지 추정이다. 확인 전에는 지역·고용형태 조건 질문이 모두 "결과 없음"으로 나온다.
  - 키: `JOBS_API_KEY`, `ANTHROPIC_API_KEY`는 Vercel 환경 변수에만 둔다.

## 7. 비기능적 요구사항 (Non-Functional Requirements)
- 동시 접속자: 1인 운영 규모. 공공 API 호출 한도를 넘지 않도록 홈 목록은 페이지당 20건만 요청한다.
- 성능: 홈 첫 화면의 공고 목록은 외부 API 응답 기준으로 로드되며, 목표는 체감상 2초 이내다 (측정 전 목표).
- 보안:
  - 고용24 채용 키는 Firestore `settings/jobs`에 있고, 보안 규칙상 누구나 읽을 수 있다. 호출 주소에도 키가 보인다. 개선: 서버 함수에서만 쓰도록 옮긴다 (AI 상담 함수에는 이미 적용).
  - AI 키는 서버 환경 변수에만 둔다.
  - 관리자 글과 설정은 관리자 계정만 쓴다.
- 안정성: 외부 API가 실패하면 패널을 숨긴다. 안내 문구는 아직 없다 (개선 항목).
- 개인정보: 질문 원문, 공고 제목을 이벤트에 보내지 않는다. 사이트 안 지원 폼은 제거를 검토한다.
- 확장성: 직업정보, 직무정보, 청년정책 API는 서비스마다 키가 다르므로 설정 칸을 따로 둔다.
